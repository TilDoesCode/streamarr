Streamarr Client — Bauplan

Eine eigene Viewer-App (Expo SDK 57 / React Native 0.86) für Android TV, iPhone/iPad, Web (inkl. iPad-Safari), dazu Apple TV und Android-Phones. Sie ersetzt Jellyfin als Wiedergabe-Oberfläche. Der Fokus liegt auf dem Kern-Loop Einloggen → Suchen → Finden → Schauen → später Weiterschauen und auf einem Player, der auf dem Fernseher wirklich gut funktioniert.

1Die Lücke im Backend

Viewer-Tokens erreichen heute nur /api/v1/viewer/*. Das sind Auth, Profil, Watch-State und Altersfreigabe. Suche, Katalog, Versionen (Releases), Resolve und Transcoding laufen über Admin- oder Maschinen-Credentials, und die darf eine App niemals mitbringen. Die Doku sagt selbst, dass „Allow transcoding“ und „Max. concurrent streams“ nur „für die Viewer-Playback-API gespeichert“ werden. Diese API existiert noch nicht. Sie ist Voraussetzung für die App und Teil dieses Plans (M1).

Schon vorhanden ✓

  • Viewer-Accounts, Sessions, Refresh, 2FA, E-Mail-Codes
  • Watch-State: Resume, Played, Next Up, History
  • Altersfreigabe pro Work
  • Server-Transcoding → HLS (fMP4) mit Plan und Direct-Play-Blockern
  • /stream/{token}: Range-fähig, spielerneutral

Fehlt für Viewer ✗

  • Katalog: Suche, Discover/Trending, Film-, Serien- und Staffel-Details
  • Versionen eines Works mit allen Qualitätsinfos
  • Playback-Start: Resolve → Fallback → Plan → Direct/Transcode
  • Durchsetzung von allowTranscoding, maxConcurrentStreams und Alter
  • CORS für die Web-App

Prinzip

  • Alle Domain-Logik bleibt im Core Server (BRIEF §1.1)
  • /stream bleibt unverändert generisch
  • Neue Endpunkte liegen im Viewer-Modul, hinter dem Modul-Gate, mit Tests und OpenAPI
  • Die App generiert ihre Typen aus v1.json

4Player-Strategie

Entschieden: nativ zuerst, VLC als Fallback. Die native Plattform-Engine (AVPlayer bzw. Media3 ExoPlayer) liefert die beste Hardware-Dekodierung, HDR/Dolby Vision, Audio-Passthrough, PiP, AirPlay und System-Integration. VLC springt nur ein, wenn nativ nicht geht.

Wer entscheidet: Ein kleines lokales Expo-Modul (media-caps) fragt das Gerät ab: MediaCodecList, HDR-Fähigkeiten des Displays und Audio-Passthrough auf Android; VideoToolbox-HW-Decode, HDR-Modi und Audio-Route auf Apple; MediaCapabilities im Web. Die App schickt dieses Profil beim Start. Der Server wählt nach der Tabelle und gibt den Grund mit („Remux: AVPlayer kann kein MKV“, „Audio DTS → EAC3“). Im Player-Menü lässt sich die Engine manuell umstellen: Automatisch · Nativ · VLC. Alle Engines stecken hinter einer TypeScript-Schnittstelle, das eigene Overlay ist überall gleich.
Risiko zuerst: M3 ist ein früher Spike auf echten Emulatoren. Dabei wird expo-video gegen react-native-video als native Engine verglichen (Media3-Optionen, Spurwahl, tvOS, Fehlerereignisse, Buffer-Kontrolle), und expo-libvlc-player (VLCKit 4 Alpha) wird als Fallback geprüft. Gemessen werden HW-Decode, Seek, Spurwechsel, Remote-Tasten und 4K-HEVC-10-bit. Fällt eine Bibliothek durch, bauen wir mit dem Expo-Modules-API eine eigene schlanke Anbindung.

5Sichtbare Zustände statt Black Box

Was Jellyfin verschluckt, zeigen wir an. Der Playback-Start ist ein asynchroner Job, den die App abfragt:

Version wählen› Verfügbarkeit prüfen› Ausweichen auf Version 2 (Version 1 tot)› Reparatur 27 % · ~3 min› Wiedergabe planen› Transcoder starten› Bereit
Fehler: Code → übersetzte Meldung + passende Aktion (Erneut versuchen · Andere Version · Qualität senken)

Versionen sinnvoll darstellen

Jede Version als klare Karte: 2160pHDR10 / DVHEVC 10-bitTrueHD Atmos 7.1DE · ENWEB-DL18,4 GB · ~24 Mbit/sbereit (lokal)empfohlen. Dazu Gesundheitsstatus und die Info, ob Direct Play voraussichtlich klappt. Gruppiert, standardmäßig die empfohlene Version.

Fehler kurz und richtig

Alle Server-Fehlercodes (age_restricted, too_many_streams, transcoding_not_allowed, no_playable_file, usenet_unreachable, transcode_capacity, …) bekommen eine übersetzte Kurzmeldung, eine Detailansicht und eine konkrete nächste Aktion. Kein „Playback failed“.

Server-Remux („Direct Stream“) NEU, Voraussetzung für nativ zuerst auf Apple

Was

  • Neuer Modus im Transcoder: Video -c:v copy → HLS fMP4 (hvc1/avc1, HDR10-Metadaten bleiben)
  • Audio kopieren, wenn das Ziel es kann, sonst EAC3 5.1 oder AAC
  • Text-Untertitel (SRT/ASS) → WebVTT-Rendition, Bild-Untertitel (PGS) → VLC-Fallback oder Burn-in beim Transcode

Wie

  • Keyframe-Index aus MKV-Cues bzw. MP4-stss, günstig über Range-Requests
  • VOD-Playlist mit echten Segmentgrenzen an Keyframes, sodass Seeken sofort und exakt funktioniert
  • Planner-Stufen: direct → remux → transcode, jeweils mit Grund

Nutzen

  • Apple-Geräte spielen MKV nativ mit HW-Decode, HDR, PiP und AirPlay
  • Web spielt viele Releases ohne Video-Neukodierung
  • Die CPU/GPU-Last auf dem Server sinkt drastisch gegenüber Volltranscode

8Fake-Usenet-Welt zum Entwickeln und Testen

Lokal ist weder ein TMDB-Key noch ein Indexer oder Usenet-Provider konfiguriert. Deshalb bauen wir den vorhandenen E2E-Harness zu einer Dev-Welt aus: echter Core Server, Mock-NNTP und Fixture-Indexer mit festem TMDB-Datensatz. Ein Kommando startet sie, sie wird auch eine Codecraft-Action.

Inhalte

  • Mehrere Filme (z. B. Blender Open Movies mit echten TMDB-IDs und Artwork) und 2 Serien mit Staffeln
  • Pro Titel mehrere Versionen: H.264/AAC MP4 · HEVC 10-bit HDR10 + EAC3 5.1 MKV · AV1/Opus · mehrere Audiospuren und Untertitel

Fehlerfälle gezielt

  • Tote Version → Auto-Fallback sichtbar
  • Degradierte oder reparierbare Version
  • Altersbeschränkter Titel
  • Zu viele Streams, Transkodierung verboten

Konten

  • anna (Erwachsene), ben (2FA), kind (ab 12)
  • Watch-Schwellen für schnelle Tests gesenkt
  • Medien per ffmpeg erzeugt und gecacht (Timecode eingebrannt)

10Ultracode-Orchestrierung und persistentes Journal

Ablauf

  • Ein Workflow pro Meilenstein, jeweils unter 10 Agenten und höchstens 2–3 gleichzeitig (Usage-Limit)
  • Jeder Bau-Agent: Aufgabe → selbst verifizieren (Build, Tests, Argent-Screenshot) → Journal-Eintrag
  • Danach unabhängige Prüfer-Agenten (adversarial), bevor etwas als fertig gilt
  • Zwischen den Workflows prüfe ich selbst, zeige dir Screenshots und committe einen Checkpoint

Journal im Repo statt im Temp-Ordner

  • docs/client/JOURNAL.md: nur anhängen, jede Aufgabe mit Start, Ergebnis, Belegen, offenen Punkten
  • docs/client/state.json: maschinenlesbarer Status pro Aufgaben-ID; Workflows überspringen erledigte Aufgaben
  • docs/client/PLAN.md: Aufgaben-IDs und Abnahmekriterien
  • Zusätzlich wird das rohe Workflow-Journal laufend nach docs/client/runs/ gespiegelt (gitignored)
  • Fortsetzen in einer neuen Session: „Lies docs/client/JOURNAL.md und mach weiter“
