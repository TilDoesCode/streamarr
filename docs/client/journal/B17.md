## Summary
Server follow-ups from the B14-B16 verifiers, no contract change. (1) A throttle-parked run keeps its remux/transcode
slot while its player asked within jobIdleTimeoutSeconds, and its resume (or a seek of that session) skips the capacity
check: with every slot taken a *new* start is refused (`transcode_capacity`), never the playing session's resume.
(2) The per-IP refresh budget counts only failed refreshes; once used up, a token that is the current/previous refresh
token of a live session still passes (one indexed read-only lookup outside the refresh lock); floods stay limited, the
per-token limit is unchanged. (3) Players are told apart by a `?p=N` tag the master playlist hands out (media and
subtitle playlists pass it into every URI; untagged requests count as address + User-Agent): one player's own far seek
and back restarts at once (0.38-0.58 s, B16 3.4-4 s), its abandoned older request never moves the run again, and the
3 s rule applies only between different players. (4) A transcode run that starts where an existing segment ends
continues it exactly (no repeated frame, no audio overlap): unshifted source clock, early seek + trim at the measured
end of the previous segment's video, audio from each track's measured end with the priming packet dropped.
(5) Error answers on the transcode routes find the playback by an HLS session index (unknown sessions: one dictionary
miss). (6) Nits: orphan doc comment, Dev World limiter log level, `fault` 400 messages, `usenet_hole` restores its
releases (faults_smoke checks it; e2e passes on the same instance afterwards).

## Decisions
- (1) Reserve instead of pre-empting: parking sets a reservation deadline (now + jobIdleTimeoutSeconds, the time a
  running job would also be stopped); every access *before* the deadline extends it, an access after it does not
  (fix round 1: the first version derived the reservation from LastAccessAt, so reading stored segments after a long
  pause revived it and the resume skipped the capacity check -> two encodes with a limit of 1). Once lapsed the
  reservation is gone for good and the resume competes like a new start (`503 *_capacity` + `Retry-After: 1` when the
  pool is full; the client retries those). Starting any run releases the reservation (a running run holds the slot
  itself). New starts get `503 *_capacity` at start time, which the client shows as a start error, not mid-playback.
- (3b) Restart pacing (fix round 1): request-driven restarts of a session take a token from a bucket of 2 refilled at
  1/s, so a seek and straight back stays immediate but flips cannot churn ffmpeg (the tag is client-chosen). A paced
  request returns "wait" and polls every 200 ms within its own budget; superseded requests of the same player drop out
  before taking a token, so the latest position wins. The parked resume at the front and the first run are not paced.
- (2) Count failures per IP (B14's flood protection keeps working for unknown/ended tokens: they never reach the
  refresh logic while the address is over budget); a live token is checked with an indexed query, not the full refresh
  path, so a flood costs one lookup per request and no gate, scan or log line.
- (3) Requester identity via a playlist tag (exact per player instance, also for two players in one app) with the
  address + User-Agent fallback for clients that fetch media playlists directly. The query is read from the request,
  not bound, so the OpenAPI document is unchanged (contract check --frozen green).
- (4) Measured instead of predicted: an absolute keyframe time list was tried and rejected (the tail segment was never
  written -> 404 end_of_stream; trim and encoder rounding still disagreed at some boundaries). The keyframe expression
  is unchanged; continuity comes from the previous segment's own timestamps, so it holds whatever the demuxer's seek
  precision or the run's cut rule. Only when the previous segment exists (resume, adjacent restart); a far seek
  restart keeps the cheaper plain seek.
- (5) Index updated wherever CurrentHls changes (SetCurrentHls) and removed on Detach.
- (6) Dev World health reset through a decorator (ResettableHealthCache) so the product cache keeps its "a live dead
  entry is never overwritten by a stale healthy one" rule.
