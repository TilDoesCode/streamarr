## Server request (for the orchestrator / backend track)
`ViewerSessionService.RefreshAsync`: when the presented token is `PreviousRefreshTokenHash` and the rotated pair was
never used (no request authenticated with the new access token, new refresh token not presented — e.g. a
`RotationConfirmedAt` set in `ValidateAsync`/`RefreshAsync`), replay the last rotation (`ReplayRotation`) instead of
revoking, for up to the refresh lifetime (or at least 24 h). Reuse after the new pair was used still revokes (theft
detection unchanged). This closes "app killed after the server rotated" on real TVs. The client already re-sends
within 30 s; jest models both rules (refresh-rotation.test.ts). Optional: Dev World runs could revoke their own
sessions (sign out) so anna stays below the 20-session cap.

### What the client does (every automatic sign-out)
Only `AccountSession.end()` signs out without the user: (a) refresh answered 401 -> `end(code)`: server
`refresh_token_reused` -> "Signed out for your security", server `refresh_session_expired` (or a bare
`unauthorized`) -> "Your session has ended"; (b) `readTokens` returns null (first read or the fresh read inside a
refresh) -> `end('session_ended')` -> "Signed out" + the vault entry is deleted. Transport errors, timeouts, 5xx and a
200 without a body never end the session (S3: retried only when the request may have reached the server, else fail
fast; S5: an unsaved pair stays in memory, write retried at most every 5 s). The text F9 saw ("Your session has
ended") is (a) with `refresh_session_expired`, i.e. the server answered 401 to the refresh.

### What the server answers (read-only, ViewerSessionService.RefreshAsync after B9)
- current token -> rotate; previous token -> replay inside 30 s or while the rotation is unconfirmed and the old token
  unexpired, else **revoke** `refresh_token_reuse` (401 `refresh_token_reused`);
- one of the up to 8 retired hashes -> **revoke** `refresh_token_reuse` (401 `refresh_token_reused`);
- no session matches (never existed / deleted by cleanup / malformed), session expired, already revoked, or account
  disabled -> 401 `refresh_session_expired`, nothing written, nothing logged.
So a plain 401 without a revoke means: the presented refresh token matches none of this session's tokens.

### Real-user bug found on the way (fixed)
`tokenVault.get` (native) caught every SecureStore read error and returned null "undecryptable after restore". But
expo-secure-store already returns null for the permanent cases (KeyPermanentlyInvalidated, BadPadding after a
reinstall) and throws only for Keystore/Keychain system errors, which are transient. A transient read error therefore
became `end('session_ended')`: the account was signed out **and the stored tokens were deleted** — also inside a
refresh (fresh read) while the process still held a valid pair.

read this device’s sign-in … you stay signed in"); `AccountStore.readTokens` falls back to the pair this process
already holds when the vault read fails, else rethrows; nothing signs out or deletes on a read error. Only "no
item" still ends the session.

### 2. Sign-out / sign-in while the secure storage keeps failing to READ (S6 P3 from V2)
- accounts-api `signOut`: an unreadable vault no longer throws; it signs out locally, uses the in-memory pair for the
  best-effort server logout if this process holds one, else skips the logout (nothing to send).
- accounts-api `completeSignIn`: reading the previous pair is best effort; the new pair is written as usual.
- account-store: every token delete (signOut, remove, stale profiles at sign-in) is best effort (`forget`); the
  in-memory pair and the unsaved pair are dropped first, so a signed-out account never keeps a usable pair here.
