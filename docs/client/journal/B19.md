# B19 — Server: release ids that played minutes ago answer release_not_found

Status: done

Intent: find why a release id reported by /devworld/playbacks for a current playback (Lighthouse S1E10/E11 on 39300)
answers `release_not_found` minutes later when a new playback starts with it; fix in the product if a release id can
become unresolvable while the release exists, or in Dev World if it is a fixture artefact. Unit + live reproduction on
Dev World 39310 (start, play a few minutes, start again with the same releaseId).

## Log
- Cause found (evidence below): not an unstable id and not the release store. The failed starts on 39300 sent the
  *previous title's* releaseId (Sintel `1361e11a…`) with the Lighthouse workId; the server answered
  `release_not_found` for that work (correct), and the client's other-version step started the right release 1 s later.
  - 39300 `/devworld/playbacks` (read-only GET, sorted by time): each failed Lighthouse start (E09 21:48:57, E10
    22:10:46, E11 22:20:32 UTC) directly follows a Sintel `mkv-dualaudio-ass` (1361e11a) playback, and is followed 1 s
    later by a ready start of the episode's own release (c143/df50/763c). Up-next starts (E09->E10 21:49:25,
    E10->E11 22:11:05, E11->E12 22:20:51) never failed. Dev World records `releaseId` only from the answer's
    `version`, so the failed rows show none: the verifier read the next row's id as "the id that failed".
  - The 39300 log (Warning) has no `Resolve failed` Error line at those times, so the failure came from the
    playback service's own check (ViewerPlaybackService ResolveAsync), which runs only when the start carries a
    releaseId that is not registered for that work, even after a re-rank.
  - Client (read only): `client/src/screens/player/play-screen.tsx:76` `useState(params.releaseId || undefined)` is
    initialised once; a deep link that reuses the mounted play screen for another workId keeps the old releaseId
    (the start effect depends on `[workId, releaseId, …]`). `playNext` (line 175) `router.replace`s without a
    releaseId, matching the up-next starts that worked.
  - Repro on 39310 (/tmp/b19/stale.py): Sintel with 1361e11a -> ready; E10 with 1361e11a -> failed
    `release_not_found` {releaseId: 1361e11a…} after 0.6 s; E10 without releaseId -> ready df505a6b005c.
  - The "id vanishes after minutes" theory is falsified: /tmp/b19/timed.py starts E10, then every minute probes the
    machine resolve for E09-E12 and restarts E10 with its releaseId (store and playback ready throughout, see
    Evidence). The release store has no time expiry (only a 10 000-entry bound; Dev World has 71 releases), the
    10-minute version cache re-registers on every search, hydration only adds.
- Fix split by owner: the server answer was correct, so the product change is only a clearer answer; the bug is in
  the client (client track, BACKLOG "Player"); Dev World's list misled the verifier, so it now shows the failure.

## Decisions
- No change to release identity, the release store or the version cache: the id is stable (sha256 of indexer + guid),
  the store has no time expiry and every search re-registers; the reported symptom does not exist on the server.
- `release_not_found` keeps its code (clients already map it to the other-version step) and gains
  `params.reason`: `otherTitle` when the id is registered for another work (message "This version belongs to another
  title.", one Information log line naming playback, work and release), `unknown` otherwise. No new error code, so no
  client change is needed to keep the current recovery; the reason lets the client and verifiers tell a client mix-up
  from a vanished version. The owning title is not named (it could be a title the viewer may not see).
- Dev World `/devworld/playbacks`: `releaseId` stays "the version that plays"; a failed start now also lists `error`
  and `errorReleaseId` (from the answer's `error.params.releaseId`), so a failed row is no longer blank.
- The client fix (reset the play screen's `releaseId` when the route params change) belongs to the client track; it is
  recorded with file/line and a test idea in BACKLOG, not done here (client/ is off limits for this task).

## Summary
"Release ids that played minutes ago answer release_not_found" is not a server or id problem. On 39300 each failed
start sent the *previous title's* releaseId (Sintel `1361e11a…`) with the Lighthouse workId: the client's play screen
keeps `releaseId` in state initialised once from the route params, and a deep link that reuses the mounted screen for
another title keeps the old id. The server answered `release_not_found` correctly, and the client's other-version step
played the right release 1 s later. Dev World's playback list shows no release for a failed start, so the verifier read
the next row's id as the failing one. Release ids stay resolvable (14-minute live probe across the version cache
expiry, a catalog refresh, unit test). Changes: `release_not_found` now carries `params.reason` (`otherTitle` |
`unknown`) and an `otherTitle` message; `/devworld/playbacks` lists a failed start's `error` and `errorReleaseId`; new
robustness check `release_id_stable`; the client fix is recorded for the client track in BACKLOG.
