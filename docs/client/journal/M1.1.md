Status: done (fix round 2 complete)

## Summary
`scripts/devworld.sh start` boots the **real Core Server** in ~3 s (warm cache) on `0.0.0.0:39300`
against a mock Usenet that encodes articles on demand from 42 generated media files (384.5 MiB),
a canned Newznab indexer and a canned TMDB fed from `fixtures/catalog.json` (7 movies, 2 series:
Pioneer One 1x6, Sherlock S1/S2 x3 with releases + S3 metadata-only; 45 releases, 10 variants).
Viewer module enabled with `anna`/`ben`(TOTP)/`kind`(12, unrated blocked)/`gast`(no transcode,
1 stream), password `streamarr`; admin `admin`/`streamarr-dev`. Writes `cache/devworld.json`
(URLs, accounts, work ids, release ids, ranks, streams, scenarios). Scenarios: dead release ranked
#1 for Cosmos Laundromat and Sherlock S01E02 (auto-fallback), degraded release ranked #1 for Tears
of Steel, two MPEG-2 legacy releases, a Pioneer One season pack, age gate. `publish` swaps
`~/.cache/streamarr-devworld/current` atomically, but only after the staged build has validated
the media and booted on a scratch port (fix round 1) and resolved every release/work pair as its
designed health (fix round 2, which also fixed a core NNTP read stall; see below).

## Log
### Exploration findings (drive the design)
- Health: any confirmed-missing article (STAT 430 or startup BODY 430) => `dead`; `degraded` only
  when some *non-startup* STAT probes fail with an exception (< 50 %). HealthChecker BODY-verifies
  the first 64 segments, STAT-samples 24 spread segments. So "degraded" needs > 64 segments and a
  STAT that drops the connection (not a 4xx answer, which counts as missing).
- Ranking/size sanity uses the *indexer-reported* size against the TMDB runtime (sample rule:
  runtime >= 15 min and < 100 MB => rejected; per-resolution MB/min bands). Short test clips with
  real sizes would all be rejected and `/api/v1/search` hides rejected releases. => the canned
  indexer reports a *nominal* size (variant nominal Mbps x TMDB runtime); real clips stay short.
- Release-year vs TMDB-year conflict makes WorkAggregator drop the match => release names use the
  TMDB year (e.g. Sprite Fright is `(2024)` on TMDB, first theatrical release NL 2024-04-06).
- Local ffmpeg 8.0.1 (Homebrew) has libx264, libx265, libsvtav1, eac3, ac3, truehd (experimental),
  dca (experimental, 5.1 needs >= 768k), libopus, aac, mpeg2video, srt/ass encoders, but **no
  drawtext (no libfreetype) and no subtitles/ass filter (no libass)**.

### Decisions
- Burned-in text without drawtext: C# renders a built-in 5x7 bitmap font into a gray8 panel
  (title / variant label / HH:MM:SS) at 1 fps, piped to ffmpeg as rawvideo and overlaid at the
  bottom. Zero extra dependencies, works with any ffmpeg.
- MockNntpServer gains an optional lazy `ArticleSource` (yEnc-encode parts on demand from the
  cached media files) + `StatDisconnects` (STAT drops the connection => indeterminate probe).
  Additive; existing tests unaffected. NNTP payload therefore costs ~0 RAM per instance.
- Titles (TMDB/IMDb ids verified via TMDB web pages + Wikidata SPARQL): movies Big Buck Bunny
  10378, Sintel 45745, Tears of Steel 133701, Elephants Dream 9761, Cosmos Laundromat 358332,
  Sprite Fright 891761 (all Blender, CC-BY), Night of the Living Dead 10331 (public domain, DE 16
  => age-gate title). Series: Pioneer One 33050 (CC BY-NC-SA, 1 season x 6 eps, NR, no stills on
  TMDB — kept null, realistic) and Sherlock 19885 (not openly licensed; no open multi-season series
  exists on TMDB; only metadata/artwork URLs are used, media is generated) S1+S2 with releases,
  S3 metadata-only (exercises "no versions").
- `officialRating` per title = DE certification if TMDB has one, else US, else first (real client
  is US-first; DE-first gives NOTLD its real FSK 16 and Sherlock FSK 12 so `kind` can watch a
  series). All captured certifications are kept in the catalog.
- Metadata captured once with `tools/capture_tmdb.py` (stdlib, public TMDB web pages).

### Blocking: `NntpConnection` stalled after a terminator on a 1024-byte boundary
- **Root cause** (as the verifier found): `NntpConnection` read through
  `new StreamReader(_stream, Encoding.Latin1)`, whose byte buffer is 1024 bytes, into an 8192-char
  buffer. `StreamReader.ReadAsync` keeps issuing stream reads while each one fills its buffer, and
  stops only on a short read or when the 8192 chars are full.
  - The stall needs three things: the body arrives after the status line was read, and the payload
    plus `.
` is a multiple of 1024 bytes but not of 8192.
  - In that case the last read is exactly full, so `StreamReader` asks the socket again. The server
    is idle and waits for the next command, so the read hangs until the 10 s read timeout. Health
    classifies the article as an IOException, so the release is `dead`.
  - Sherlock S02E02, article 41: 273,408 bytes = 267 x 1024.
- **Fix** (`server/src/Streamarr.Usenet/Nntp/NntpConnection.cs`): the `StreamReader` is gone.
  - `ReadBoundedLineCoreAsync` refills its 8 KiB buffer with one `_stream.ReadAsync` into a byte
    buffer, which returns whatever has arrived. It then decodes with `Encoding.Latin1.GetChars`,
    which maps byte to char 1:1 and has no decoder state.
  - `ThrowIfNotConnected` and `ReadBodyToPipeAsync` check `_stream` instead of `_reader`.
  - `CleanupConnection` disposes the stream before the writer. This is the old order: the reader
    used to close the stream first.
  - The line bounds, timeouts and cancellation are unchanged.
  - This is a **product fix, not only a harness fix**: a real provider hits the same pattern for
    about 1 in 1024 articles whenever the body arrives after the status line. It is a candidate
    for the next release notes.
- **Regression test** (`Streamarr.Usenet.Tests/Nntp/NntpClientTests.cs`):
