# B9 — Server: series next episode prefers an active replay, next-up without versions, refresh replay after an app kill

Status: done

## Summary
One shared rule (`CurrentEpisodeRule.ActiveResume`) picks a series' current episode: the most recently played episode
with a resume point wins when its `lastPlayedAt` is newer than the latest `playedAt` in that series, else next up as
before. It drives `/watch/next-up` (returns the replayed episode with its position, `lastWatchedWorkId` = it), the
series `watch.nextEpisode` (fallback resume also uses the rule) and continue watching (`/watch/resume` keeps only the
series' active resume point; stale ones older than a later completion are left out). Next-up/continue items and
`nextEpisode` carry `available`: false when the last version lookup found no version that is not known dead; the
next episode is never skipped (Sherlock S3E1 comes back with available=false). Availability is persisted next to the
spec summary (new nullable column, migration `AddCatalogSpecAvailable`).

(3) Refresh rotation after an app kill: `RefreshAsync` answers the previous refresh token with the same rotated
pair while that pair is unused (no request authenticated with its access token, its refresh token never presented)
and the previous token is within its own lifetime — beyond the 30 s grace. A late replay whose access token has
expired gets a fresh access token with the same rotated refresh token. Once the pair was used, the previous token —
or any of the last 8 older tokens of the session — revokes the session (`refresh_token_reused`). Migration
`ViewerSessionRotationReplay`: `RotationConfirmedAt`, `PreviousRefreshExpiresAt`, `RetiredRefreshTokenHashes`.

## Decisions
- `available` unknown (no version lookup yet) = `true`, and the item is queued for the spec warm-up, so the next
  fetch is truthful; a synchronous indexer search on list endpoints would break the "never on the request path"
  rule of the warm-up. Opening the season with `availability=true` records it at once (as the series page does).
- `available` is required `bool` on `NextUpItemResponse`, `bool` (default true, not required) on
  `CatalogNextEpisodeDto`, and `bool?` on `WatchStateResponse` (continue watching only, null on history/state/series).
- "Newer" is strict (`>`): equal timestamps leave next up (stable under the tests' manual clock).
- Next up still needs a played episode in the series (anchor); a series with only an in-progress episode stays
  in continue watching and in `nextEpisode` (unchanged behaviour).
- Continue watching shows one episode per series (the active resume point) — two paused episodes of one series now
  show only the most recent; consistent with "all surfaces agree".
- Availability = at least one release not known dead (same test as `versionCount`); season row = any episode.

- (3) First use = `ValidateAsync` with the rotated access token (atomic update guarded by the access hash) or the
  rotated refresh token presented (that rotates again, which retires the older token). The 30 s grace stays as is
  (two tabs refreshing at once still get one pair even after one tab used it).
- (3) Old-token lifetime = the expiry it had before the rotation (`PreviousRefreshExpiresAt`); sessions rotated
  before the migration have it null and keep the old grace-only behaviour.
- (3) Expired access token on a late replay: mint a fresh access token (refresh token unchanged, encrypted pair
  updated) instead of handing out a dead one; the client then needs no extra round trip.
- (3) "Even older token -> revoked": the last 8 retired hashes are kept per session (space-separated, looked up only
  when neither current nor previous matches); older than that stays a plain 401 `refresh_session_expired`.

Security (item 3), all reproduced with raw HTTP (/tmp/b9v/phase*.py):
- Unused state cannot be reset with the previous token: replays never write RotationConfirmedAt/RotatedAt/
  PreviousRefreshExpiresAt; only a rotation with the current token clears it (code + DB check). Replay never extends
  the old token (PreviousRefreshExpiresAt fixed at rotation).
- Retired token while the newest pair is unused -> 401 and session revoked; older token after two rotations -> reused.
- Expired access on replay (DB-forced): new access token, same refresh token, old access 401, still unconfirmed; the
  re-minted access token confirms; a later replay -> 401.
- Sign-out (bearer), sign-out-others, password change, admin disable: previous token and both pairs -> 401.
- Admin `/config/viewers/{id}/sessions` and `/viewer/me/sessions` expose no token/hash fields; Dev World log has no
  svr_/sva_ strings (reuse warning logs the session id only). Retired hashes: DB lookup by hash + exact split match.
- Migrations on a DB built by the pre-B9 snapshot (sessions rotated unused, rotated used, never rotated, 40 s old):
  both applied, all sessions keep working; the pre-migration previous token -> refresh_token_reused (grace-only, as
  documented).
