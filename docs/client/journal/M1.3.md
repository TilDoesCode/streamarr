# M1.3 — Viewer playback API

Status: done

## Summary
`/api/v1/viewer/playback` starts a version on one device asynchronously: `POST` → `202 { playbackId, state }`, then
`GET {playbackId}` walks `queued → resolving → (fallback) → (repairing) → planning → starting → ready | failed` with
`attempts[]` per hop, `fallbackFrom`, the `version` (VersionDto) and repair progress/ETA. It reuses the resolve pipeline the
two-phase admission uses (health check, bounded auto-fallback, PAR2 repair; client `streamarr-viewer`, requester = viewer)
and M1.4's planner/remux/transcode sessions. The decider follows PLAN §2 (native direct > native remux > VLC direct if
`vlcAvailable` > transcode if `allowTranscoding`), honours engine/quality/language/subtitle-mode preferences and per-codec
device limits, and handles image subtitles (VLC → **new burn-in transcode** → without, said so). `ready` returns method,
engine, a capability URL relative to the server origin (`/api/v1/stream/{token}` or `/api/v1/transcode/{cap}/master.m3u8`,
no auth headers), full track lists with `deliveredAs`, `decision.reasons`/`skipped` with stable codes + params,
`streamToken`, `resumePositionTicks`; `failed` returns `error { code, message, params }` + `suggestedActions`. `switch`
(tracks/engine/quality/version/`stepDown`, same id, new revision, old URL valid 30 s), `stop` (closes sessions, frees the
slot), heartbeat via `/viewer/watch/progress` with `playbackId`, idle expiry, per-device ownership (404 elsewhere),
`allowTranscoding` (full transcodes only), `maxConcurrentStreams` (recent heartbeat, 409 naming the other device), age gate
(403 on start and switch). Also fixed a pre-existing M1.4 bug found while testing burn-in: restarted transcode runs with
stream-copied audio began the audio up to 30 s before the video. Contract, docs, web + client types updated; server
247/441/35/946 green; e2e 316/316 on the tree and on the published snapshot `20260929T093959Z-66668`.

## Intent
Add `/api/v1/viewer/playback` (async POST → playbackId, GET state machine queued → resolving →
fallback → repairing → planning → starting → ready|failed with attempts/version/decision/mediaInfo,
switch, stop) on top of the existing resolve pipeline (health check, auto-fallback, repair) and the
M1.4 planner/remux/transcode sessions. Engine selection per PLAN §2 (native direct > native remux >
vlc direct > transcode), user preferences, default track selection by language, enforcement
(allowTranscoding, maxConcurrentStreams with heartbeat, age gate), watch-progress heartbeat with
`playbackId`, idle expiry, per-viewer-session ownership (404 for others). Contract, docs, web/client
types, tests with fakes, end-to-end on Dev World 39310 with ffprobe/hlssim, then publish.

### Decisions
- Layout: `Viewers/Playback/` (`PlaybackContracts`, `DeviceCaps` (profile parsing + canonical names),
  `PlaybackDecider` (preferences, track selection, §2 ranking), `PlaybackPorts` (`IPlaybackResolver`,
  `IPlaybackMedia` + server implementations), `ViewerPlaybackService` (registry, state machine, sweep)) and
  `Viewers/Controllers/ViewerPlaybackController`. Same attribute stack as the catalog controller.
- Resolve reuse: the playback runs the same `ResolveService` pipeline the two-phase admission runs (health
  check, bounded auto-fallback, repair engagement, progressive/artifact playback) with client
  `streamarr-viewer` and requester = viewer id (M1.2 note), through the ownership-aware internal overload. It
  gained an optional `IResolveObserver` (hop started / hop finished) so `attempts` and the `fallback` state are
  visible while the resolve runs. Wrapping `PlaybackAdmissionService` itself was not useful: its phases are only
  preparing/ready/failed and its claim/ownership model is for the Jellyfin plugin; the viewer playback needs its
  own lifetime (switch, heartbeat, idle expiry, per-device ownership).
- Repair: a dead resolve that engaged a repair job (no healthy fallback, `whenNoFallback` policy) turns the
  playback into `repairing` with the job's progress/eta (`RepairCoordinator.GetJobByRelease`), polled every 2 s;
  when the job is ready the release is resolved again (served from the local artifact); failure → `repair_failed`.
- Async model: POST validates, runs the age gate and the stream limit synchronously (so 403/409 are HTTP errors),
  then answers `202` with the state; the work runs in the background under the playback's own cancellation.
  `queued` = waiting for a resolve slot (`MaxConcurrentResolves` is non-blocking in ResolveService; the playback
  retries for up to 60 s). States: queued → resolving → (fallback) → (repairing) → planning → starting → ready|failed.
- Release choice: no `releaseId` → rank 1 of the catalog ranking (M1.2 note). A given `releaseId` must be
  registered for the requested work (the age gate ran on that work); an unknown one triggers one re-ranking
  (re-registers releases after a restart) before `release_not_found`. `version` comes from the cached ranking
  without an indexer search when present, else from the registration with `rank: 0`.
- Decision (pure, `PlaybackDecider`): per candidate it runs M1.4's `TranscodePlanner.Decide` with a
  `ClientProfile` built for the source codec from the engine's capabilities; order auto = native direct → native
  remux → VLC direct (vlcAvailable) → transcode (allowTranscoding); `native` never uses VLC; `vlc` = VLC direct,
  then transcode to VLC. Image subtitle the native engine cannot render: VLC direct → burn-in transcode → the
  normal order without the subtitle (+ `subtitle_not_deliverable`). Device limits the planner cannot express are
  checked first (per-codec max size → `video_size_unsupported`, per-codec audio channels for direct play →
  `audio_channels_unsupported`). Server ffmpeg off/unusable removes remux/transcode (`transcoding_disabled`,
  `ffmpeg_unavailable`). The first viable candidate that starts wins; an HLS start failure (e.g.
  `remux_not_possible` when no keyframe index exists) falls through to the next one.
- Burn-in: M1.4 transcodes had no burn-in. Added `TranscodeLimits.BurnInSubtitle`: a transcode overlays the
  selected image subtitle (`-filter_complex [0:v]…[base];[base][0:s]overlay…[vout]`, CPU decode path, scale after
  the overlay), reason `subtitle_burned_in`, `deliveredAs: burnedIn`. Text subtitles still cannot be burned in
  (no libass in the local ffmpeg) and transcodes still carry no WebVTT renditions.
- allowTranscoding=false only removes the full-transcode candidate; remux (incl. audio conversion) stays.
- Stream limit: active = preparing, or ready with the last activity (ready, heartbeat, switch) within
  `Streamarr:ViewerPlaybackHeartbeatSeconds` (60). At the limit, the same device's older playbacks are replaced;
  another device's → `409 too_many_streams` with params `limit`, `device`, `workId`, `title`. Failed playbacks do
  not count. Idle expiry: no poll/heartbeat/switch for `Streamarr:ViewerPlaybackIdleSeconds` (600) → stopped.
- Ownership: a playback belongs to the viewer session (device) that created it; other viewers and the same
  viewer's other devices get `404 playback_not_found` on GET/switch/stop and no heartbeat.
- Heartbeat: `/viewer/watch/progress` with a server `playbackId` (same device, same work) fills `releaseId` and
  `streamToken` (so pre-download and playback ranges work), keeps the playback active and touches its HLS
  session; `event: stop` ends the playback like POST stop. Unknown ids keep the old client-chosen-id behaviour.
- Stop: closes the playback's remux/transcode sessions (current + switched-away) and forgets it; the stream
  capability is left to its normal TTL/LRU so a later playback of the same version reuses it without a new
  health check (the resolve reuse path, like Jellyfin re-opens).
- Switch: same `playbackId`, `revision` + 1; release change → resolve again, else re-plan on the live
  capability. The previous HLS session stays valid until 30 s after the new revision is ready (then closed by the
  sweep); on a failed switch it stays until stop/expiry. `stepDown: true` excludes the current method+engine.
- URLs are capability paths relative to the server origin (`/api/v1/stream/{token}`,
  `/api/v1/transcode/{cap}/master.m3u8`); players need no auth headers.

## Open issues / follow-ups
- **pending-ios:** no Xcode, so the URLs chosen for the Apple TV and Safari profiles were not played in AVPlayer/Safari
  (API + ffprobe + hlssim only). M1.4's Apple checks (`mediastreamvalidator`, `X-TIMESTAMP-MAP`) are still open too.
- No device/browser playback in this task: the URLs are M1.4's stream/HLS capabilities (M1.4 verified hls.js in Chrome);
  M3.1 plays them on devices.
- **Repair** is covered with fakes only: the Dev World has no PAR2-repairable release (M1.1 open issue).
- **Text subtitles with a transcode** (e.g. `maxHeight` below the source on an MKV with SRT) are not delivered
  (`subtitle_not_deliverable`): transcodes carry no WebVTT renditions and text burn-in needs libass. Follow-up: WebVTT
  renditions for transcodes, or client-side sidecar rendering.
- Burn-in after a seek: Matroska sources show a subtitle already on screen (demuxer seek-back ≤ 30 s); other containers
  show the next one. Burn-in forces software decode (CPU cost on large sources).
- Playbacks live in memory: a server restart forgets them (clients get `404 playback_not_found` and start again). Stop
  leaves the stream capability to its TTL (fast re-open without a health check).
- GET polls keep a playback from idling out but do not count as stream activity; a player that never reports progress
  stops counting toward `maxConcurrentStreams` 60 s after `ready`.
- Pre-existing, not M1.3: at host shutdown `ViewerMailer.ExecuteAsync` throws `OperationCanceledException`, which the host
  logs as `BackgroundService failed` + `FTL … StopHost` (seen in test logs; harmless but noisy).
- Production CORS: capability URLs used cross-origin by a web client need the server's CORS policy (the Dev World allows
  any origin); a same-origin web client needs nothing.

### Non-blocking
- **Dead code:**
  - `ViewerPlaybackService.Count` (internal) is never read.
  - `PlaybackDecision.Tracks` is set but never read.
  - `HlsRendition.Mode` is constructed but never read.
  - `DeviceCaps.Platform` is validated and stored, but no decision uses it.
- **Doc inconsistency:** `docs/viewers.md` (*Playback*) says capability URLs "stop working when the playback ends".
  That is true for HLS, but a direct-play `/api/v1/stream/{token}` still answered `206` after `stop` (measured). This
  is by design: `docs/api.md` correctly says the capability lives out its TTL (24 h here). The same applies after an
  admin tightens the age limit: the running direct URL keeps working.
- **Engine order is ignored:** `DeviceProfileDto.Engines` is documented as "in the device's order of preference", but
  the server always ranks native/web before VLC (§2). A second native/web entry is silently dropped (only the first is
  used). The docs should say that the order does not matter.
- **Sticky bad track index:** a switch to a non-existent track (e.g. `subtitleStreamIndex: 99`) fails with
  `unknown_subtitle_stream`, as it should. But the index stays on the playback, so a later switch that changes only
  the audio fails again until the client sends a valid subtitle index. The recovery works: a switch with a valid index
  was ready again. In the same way, `stepDown` on a playback whose last switch failed silently excludes nothing.
- **Activity is only polls, heartbeats and switches:**
  - HLS segment fetches do not count. In the short-timing run, playback A was expired and its remux closed while its
    `0.m4s` was being fetched every 5 s. Documented, but M4.2 must send heartbeats during long pauses too.
  - A playback whose switch failed stops counting toward `maxConcurrentStreams`, while its previous rendition stays
    served until stop or expiry. This is an edge case for `gast`-type limits.
- **Double probe per start:** the resolve runs its ffprobe (per-release cache), then `ProbeSourceAsync` probes the same
  capability again. This is not measurable on the Dev World (ready in < 1 s), but costs an extra read on real Usenet.
- **§2 interpretation:** lossless TrueHD/DTS on Android TV without passthrough is remuxed with lossy E-AC-3
  conversion. VLC would decode it losslessly. This follows the numeric ranking (remux before VLC). The "exotic audio
  without passthrough → VLC" example in §2 therefore never triggers. Worth a sentence in the docs or an M3.1 check.
- **Version rank without a cached list:** a start with an explicit `releaseId` whose version list was never fetched
  reports `version.rank: 0, recommended: false` (documented). The client should not show that as "not recommended".
