## Reconciliation, migration and follow-up audit

**Cost and recovery.** `reconciliation-probe` seeds 50 real ready download rows across five viewers and admits 100 synthetic leases at the maximum configured limits. It performs 100 sweeps: **200 SELECTs**, **0 cancelled valid leases**, median **0.44 ms**, worst **67.41 ms** on this loaded machine. With no leases it performs **0 SQL reads**. The periodic loop runs after each sweep plus a 500 ms delay, so work does not overlap itself. A forced recoverable `InvalidOperationException` in a read is logged/caught; the next sweep completes. Normal SQLite/EF failures are explicitly caught. This establishes query cost/recovery for the tested scale, not provider or network saturation. The deterministic stale-read race is V4-01.

**Migration and winner.** The legacy seed project really executes the original hardening migration from archived a48a0755. Upgrading it, and separately upgrading a pre-DL database with nine later inserted download records, preserves all rows, pipe tuples and non-ASCII identities. For the specific new migration boundary, start at `ViewerDownloadsLifecycle` with `Phone`, `phone`, `PHONE`, identical viewer/clientRef, oldest row owning `DeviceKey=d:phone` and later historical duplicates having null keys. `ViewerDownloadsDeviceIdentity` makes all three stored device IDs `phone`; **dup-old retains the unique key**, dup-mid/dup-new remain unkeyed. The compound unique index is on **DeviceKey**, not DeviceId, so normalizing DeviceId introduces **no unique-index conflict**. Attempting to assign dup-new that same key still fails with SQLite uniqueness error. No record is discarded or arbitrarily substituted. The earlier lifecycle migration already selects the oldest `(CreatedAt, Id)` duplicate when deriving the key; the new migration preserves that decision.

**Post-commit work.** Security retirement is persisted with session revocation, generation and revision increment in one transaction. A request cancellation or lost notification cannot undo it. `NotifyAsync` awaits the listener, uses `CancellationToken.None`, logs exceptions and relies on reconciliation for transfer cleanup; it is not an unobserved fire-and-forget task. Its current listener loops over the transaction's bounded retired-ID list and does no SQL. The broader password/2FA/disable/delete follow-ups also run independently of the request token. Access-change work may await policy/DB operations and has no new overall timeout; no hang, retry storm or lost exception was reproduced. Forced lifecycle exceptions/cancelled lock waiters still release the DB transaction and keyed locks. V4-01 is the identified targeting defect in otherwise completed follow-up work.

**Accounting and shutdown.** Final flush requeues the cancelled current/unwritten batch and has its own timeout; the first and second-write cancellation cases now save each count once. Overlapping range requests, complete and graceful restart preserved an exact 327,680-byte total in the live probe. The deliberate hard-kill case again lost one unflushed 65,536-byte telemetry chunk while retaining capability, ETag and identical resumed bytes; this remains the documented best-effort accounting boundary, not a new finding. Shutdown/restart tests completed without a reconciliation-loop or accounting-flush hang.
