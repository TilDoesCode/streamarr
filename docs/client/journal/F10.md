# F10 — The player catches and explains every state

Status: in-progress (S1–S5, S4b–S4d, S8, S9a fixes, B13b committed up to 4593df6; S4f and S4g (code review S4c-S4f fixed) done 2026-10-05 in `../streamarr-f10`, not committed; S6/S7 native probes in the parallel worktree `../streamarr-f10n`; live checks S9)

## Intent
Implement the user requirement of 2026-10-05 00:50 (PLAN § 5 "I"): the viewer never sees a generic error, a black
screen or a frozen picture. Every player state is either compensated automatically (wait, reload, new start at the
position, lower quality, step-down, other version) or explained with one specific de/en hint and an action. One
health watchdog per engine (frames, clock, audio), one error taxonomy with a compensation ladder and budgets, jest
tests per matrix row with fake engines, then live runs with Dev World fault injection (B12) on every engine.

F10a (research + design, no devices) is done; F10 S1–S9 are the build slices.

**Decisions.**
- **Probe cost.** The health ticker runs only where an engine has `readHealth` (web now). expo-video and VLC get
  their probes in S6/S7; no extra 1 s JS work on TV until then (Q1-25 tick budget). VLC keeps its own `checkStall`
  until S7 moves it into the watchdog.
- **Frames source on web.** `getVideoPlaybackQuality()` once per tick instead of a permanent
  `requestVideoFrameCallback` loop (one JS callback per frame); rVFC stays for the first-frame detection. On
  **Safari native HLS** rVFC never fires (F8) and the counters are unproven, so frame counts are reported only once
  they were seen moving on that element; before that no picture rule runs there (never guessed). hls.js/MSE counters
  are trusted from the load on.
- **Luminance only for MSE data.** The Dev World media is cross-origin from the web app (Metro :8081 → server :39300,
  no Metro proxy); Dev World answers `Access-Control-Allow-Origin: *` on `/api/v1/stream` and `/api/v1/transcode`
  when the request has an `Origin` (`DevWorldHttp.cs:20-35`). hls.js loads with XHR (Origin sent, CORS passed) into
  MSE, so its picture is readable; a plain `<video src>` sends no Origin and taints the canvas. I did **not** set
  `crossOrigin="anonymous"` (a production server without CORS headers would then not play at all). The luma rule is
  deliberately narrow: pure black (brightest pixel ≤ 2) from the load on, for 20 s of clock, within the first 60 s —
  dark scenes and fades never qualify.
- **Audio presence.** `webkitAudioDecodedByteCount` counts only once it moved on that element (a counter that stays
  0 under some MSE build must not turn every hls.js playback into "no sound" + step-down). No WebAudio analyser:
  `createMediaElementSource` reroutes the element's audio and cross-origin media plays silence through it — the probe
  would cause the failure it looks for.
- **Black/frozen resume position** is where frames last moved (`watchdog.lastGoodPosition`), not the running clock.
- **Bug found by the D39 test and fixed:** a recovery step that already ran (source reloaded, waiting for a picture)
  blocked the start and stall budgets (`calm` required `!recovery`), so a reload that never showed a picture spun
  "Resuming at …" forever. Only a *pending* step holds the budgets now (`statusTick`).
- Harness: probing is opt-in (`harness.features.probe = true`); scripted engines without it keep the S2–S4 behaviour
  (their clocks stand still between events, which a probe would rightly call frozen).

### FAIL rows — repro and suspected code

1. **START / C21 / C12 / C08 / D29 / D36 — black 0:00 with neither spinner nor hint (root cause shared).**
   - Repro: arm `{"fault":"seg_delay","scope":{"next":"anna"},"target":"video","params":{"ms":6000},"mode":{"count":2}}` and open `/play/new?workId=tmdb-movie-45745&start=90` in Chrome. You get 6.5 s of black 0:00 with no spinner.
   - Mechanism: in hls.js mode the web engine emits a `time` event with `currentTime 0` before hls.js applies its `startPosition`. The `startSeek` guard in `client/src/player/engines/web-engine.web.tsx:223-236` only applies in native mode, where `startSeek.target` is 0. The controller treats any clock ≥ 0.5 s away from `loadPosition` as a picture, at `client/src/player/controller.ts:700` (`if (!this.pictured && Math.abs(event.position - this.loadPosition) >= 0.5) this.onPicture()`).
   - Result: `onPicture()` (`controller.ts:918-924`) sets `pictured=true` and `loadingSince=0`. That removes the loading spinner (`recovery/status.ts:89-94`) and the start budget (`controller.ts:1059-1061`), so a source that never delivers stays black for good. This is the C12 after step-down, D36 and C21 cases.
   - Every reload, new start or step-down at position > 0 (`controller.ts:744-748`) hits the same path.
   - Fix direction: count a picture only on the engine's `firstFrame`, or on a clock that moved from the load position.
2. **C10 503 (and the interim hint of C10-404, C17, P4) — a server error is shown as "buffering" with "Lower quality".**

3. **C08 — a slow transcode is called "Slow connection 0.6 of 2.2 Mbit/s".** `stallHint` (`recovery/status.ts`, after line 125) compares the hls.js bandwidth estimate with the bitrate.
