## Summary
Root cause of the iPhone -12927: every transcode of an HDR source inherited the source's colour tags, because ffmpeg 8
takes the encoder's colour tags from the frames, and the Dev World's ffmpeg has no zscale, so no tone map ran. The output
was H.264 tagged bt2020/smpte2084 with mastering-display/CLL metadata under `VIDEO-RANGE=SDR`. The VideoToolbox GPU
tone map tagged bt709 but still carried mdcv/clli. Every HDR-sourced transcode now ends its filter chain with
`FfmpegArgumentBuilder.SdrTagChain` (setparams bt709/tv + sidedata delete), on every encoder and path including burn-in.
Remux passthrough keeps PQ/HLG and SDR sources keep their own tags. A guard in the e2e (`colour_check`) ffprobes
init + segment 0 of every remux/transcode against VIDEO-RANGE. It fails on the pre-B6 build and passes now.
B5 follow-ups are done: the splitter only throws InvalidDataException (bounded trun) and the route answers 500
`rendition_split_failed`; NAME/label is the native language plus the delivered codec; there is one codec per remux
audio group; fMP4 audio tracks carry their language; docs are fixed; the sync helper is removed; the admin plan lists
audioRenditions.
