# M1.2 — Viewer catalog API

Status: done

## Summary
`/api/v1/viewer/catalog` ships six viewer endpoints as thin facades over existing services:
`search` (TMDB candidates), `discover` (trending/popular movie and series rows, TMDB lists cached
6 h), `movies/{id}` and `series/{id}` (details incl. title logo + certification, the viewer's watch
state, access; series add season summaries with played counts and a `nextEpisode` with reason
`start|next|resume`), `series/{id}/seasons/{n}` (episodes with watch state; `availability=true`
overlays version counts from the season fan-out), and `works/{workId}/versions` (ranked
`VersionDto`s parsed from the release name: resolution, source, codec, bit depth, HDR incl. Dolby
Vision, audio/channels/Atmos, languages, subtitle hints, edition, group, size, estimated bitrate,
age, current health, viewer-scoped local pre-download, rank, recommended; optional heuristic
`predictedMethod` from a compact device profile via the M1.4 planner). No NZB URL, indexer name/id,
key, score or grabs leaves the server. Every endpoint: viewer policy, module gate, password-change
gate, age policy (lists hide, details/seasons/versions `403 age_restricted` with `error.params`),
standard envelope (also for malformed values). Search/discover/details/seasons never touch an
indexer; versions and `availability=true` share a single-flight 10-minute cache with `?refresh=true`.
The Dev World has discover rows, logos and two metadata-only movies; published as
`20260929T040445Z-24499`.

## Intent
Add `/api/v1/viewer/catalog` (search, discover, movie/series/season details, work versions) as thin
viewer-facing facades over the existing TMDB, search/rank, health, availability and watch-state
services, with viewer auth, module gate, password-change gate, age policy and the standard error
envelope. New `ITmdbClient` trending/popular methods (default empty), cached discover rows, Dev World
fixtures for the rows, VersionDto derived from the parsed release, tests, OpenAPI, web/client types,
docs (`docs/api.md` §13, `docs/viewers.md`). Test on 39310, then publish the Dev World.

### Decisions
- Layout: `Viewers/Catalog/` (contracts, `ViewerCatalogService`, `ViewerVersionCache`, `VersionMapper`,
  `PlaybackPredictor`) + `Viewers/Controllers/ViewerCatalogController.cs`; same attribute stack as the

- Facades only: TMDB via `ITmdbClient`, ranking via `SearchService` (movies, `tmdbId` path like the Dev
  World warm-up) and a refactored `TvCatalogService.GetSeasonReleasesAsync` (episodes/packs; the admin
  `/tv/.../seasons/{n}` maps the same result, behaviour unchanged), health via `IReleaseHealthCache`,
  local availability via `SessionManager.ListLocalReleaseAvailability(client "streamarr-viewer",
  requester = viewer id)` (M1.3 must resolve with that client/requester), watch state via the existing
  services, age gate via `ViewerContentPolicy.Decide`.
- Age gate on lists needs the certification, which TMDB list/search results do not carry: for restricted
  viewers (maxAge set) each list item is looked up with the (cached) detail call; unrestricted viewers
  cost no extra lookups. Lookup failures hide the item for restricted viewers (same rule as
  `rating_unavailable`). Details/season/versions answer `403 age_restricted` with `params` (reason,
  rating, minimumAge, viewerMaxAge) — additive optional `error.params` on the shared envelope
  (omitted when null), also what M1.3 needs.
- Discover: new `ITmdbClient.GetTrendingAsync/GetPopularAsync(mediaType)` (default: empty);
  `TmdbClient` uses `trending/{movie|tv}/week` and `{movie|tv}/popular`; `CachingTmdbClient` caches list
  calls with a separate `Tmdb:DiscoverCacheTtlHours` (default 6 h). Rows: trending-movies,
  trending-series, popular-movies, popular-series (empty rows omitted).
- Versions: short-lived single-flight cache per movie / per season (default 10 min,
  `Streamarr:ViewerVersionsCacheSeconds`), `?refresh=true` recomputes; results with a failed indexer are
  not cached. Health and local availability are overlaid at read time (dead releases from the health
  cache are dropped, like `FindUsable`). Rank = position in the server's ranked list; `recommended` =
  rank 1 (what the server would pick). No NZB URL, indexer name/id, score or grabs in VersionDto.
- Parser additions in Core (tested): bit depth (`10bit`, `Hi10P`, `Main10` ...), all HDR formats
  (DV + HDR10 fallback), subtitle hints/languages (`Subbed`, `MultiSubs`, `HC`, `NLSubs`, `VOSTFR` ...).
  VersionDto infers 10-bit for HDR formats when the name has no explicit bit depth (HDR requires it).
- Logos: `TmdbMatch.LogoUrl`, real client appends `images` (`include_image_language=<lang>,en,null`);
  Dev World catalog gets captured logo URLs (capture tool extended).
- Prediction: optional compact device profile as query params (videoCodecs, audioCodecs, containers,
  hdrFormats, supports10Bit, maxAudioChannels, maxHeight, maxBitrateKbps) → `predictedMethod` per version
  from M1.4's `TranscodePlanner.Decide` on a synthetic source built from the parsed name; every assumption
  (container unknown → mkv, unknown audio/resolution, DV profile unknown) is reported as a note.

## Open issues / follow-ups
- TMDB's caching decorator turns transient failures into `null`, so a TMDB outage with a cold cache
  shows as `404 title_not_found` on details (an uncached `TmdbTransientException` maps to
  `503 catalog_unavailable`). Distinguishing them needs a change to `CachingTmdbClient`'s contract.
- Restricted viewers: each list item costs one TMDB detail lookup (cached 24 h, 4 concurrent), so the
  first discover of a restricted viewer against real TMDB can take a few seconds (≤ 80 lookups).
- `predictedMethod` cannot know the container (names rarely say MKV/MP4; MKV is assumed and reported)
  nor image subtitles or the Dolby Vision profile; MP4 releases without "MP4" in the name are predicted
  as remux for MP4-only players (e.g. the Dev World WEB-DL releases on Safari).
- Model-state errors of the other viewer controllers (e.g. `watch/resume?limit=abc`) still use
  ProblemDetails; the new filter is only on the catalog controller.
- Real TMDB trending/popular/logo parsing is covered by stubbed HTTP tests only (no TMDB API key here).
- `version` ties: movie lists use the search order (score, then size); `IReleaseStore.FindBest`
  (resolve without `releaseId`) breaks ties by title. See the M1.3 note below.

### Non-blocking
- **TMDB outages look like "not found" / "nothing there".** I confirmed this with a throwaway test in a /tmp copy.
  `CachingTmdbClient` (the production wiring) turns a `TmdbTransientException` into `null` or `[]`. As a result:
  - details, series, seasons and versions answer `404 title_not_found`;
  - `search` answers `200` with no items;
  - `discover` answers `200` with no rows;
  - restricted viewers see every item hidden.
  The `503 catalog_unavailable` branch in `ViewerCatalogService.TmdbAsync` and `RowAsync`, which OpenAPI declares for
  search/movies/series/seasons/versions, can only be reached with a raw `ITmdbClient` fake. The builder listed the
  details case; search and discover are affected too. This has to be decided before M4.1 builds its error states.
- **Dead code:** `SeasonReleaseOverlay.SeasonPackReleaseIds` (`TvCatalogService.cs`) is built but never read.
- **`?refresh=true` has no per-viewer limit.** Each call replaces the shared cache entry and takes a slot in the
  server-wide `SearchConcurrencyGate`. A viewer app looping refresh can therefore push admin and Jellyfin searches into
  `429`. The indexer's 60 s response cache keeps the real indexer load low.
- **Prediction default:** sending `hdrFormats=hdr10` without `supports10Bit=true` predicts HDR sources with
  `bit_depth_unsupported`. An HDR-capable profile implies 10-bit, so the default is a trap for clients (document it or
  infer it).
- **Subtitle parser:** `VOSTA` is mapped to Spanish (`es`). In French release naming the `A` normally means
  *anglais*; Spanish uses `VOSE`.
- **Error envelope keys:** catalog 4xx bodies still carry the shared envelope's `"host": null, "indexerId": null`.
  This is a pre-existing shape and no value leaks. Omitting null values the way `params` does would read cleaner for
  a viewer API.
- **OpenAPI:** `search` and `discover` do not declare `403 password_change_required` / `404 module_disabled`. The other
  viewer controllers omit them the same way.
- **Dev World:** the two metadata-only movies (Agent 327, Wing It!) depart from M1.1's "each title has 2-5 releases".
  This is deliberate (the empty-versions state), capped at 2 by `WorldPlan` and documented. Their artwork and the
  captured logos all load (`200 image/*`).
- **Track boundary:** `client/src/api/schema.d.ts` (untracked, client track) is byte-identical to the regenerated
  web file (`ef43b55a…`). The checkpoint must decide whether it goes with M1.2 or M2.3.
