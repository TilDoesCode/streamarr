# B11 — Server: precise refresh failure codes, refresh failures logged, session tombstones

Status: done

## Intent
Split refresh 401s into refresh_token_reused / refresh_session_expired / refresh_session_revoked (params.reason) /
refresh_token_unknown; log every refresh failure (Information, case + session/viewer id, no token material);
keep 30-day tombstones of deleted/revoked sessions (hash only) with cleanup + migration; tests, docs, OpenAPI.
Source: F8 S6 "Server request" (streamarr-f8/docs/client/journal/F8.md, read-only).

## Summary
`POST /api/v1/viewer/auth/refresh` now says which case a 401 is:
- `refresh_token_reused` (unchanged, B9 theft detection; this request revoked the session);
- `refresh_session_expired` — session (or its tombstone) found and its refresh window is over;
- `refresh_session_revoked` + `params.reason` — `signed_out`, `revoked_by_viewer`, `session_limit`, `admin`,
  `password_changed`, `account_disabled`, `token_reused` (session earlier ended by reuse), `other` (fallback);
- `refresh_token_unknown` — malformed, never issued, or no session/tombstone matches (deleted > 30 days ago, a device
  restored from an old backup/emulator snapshot). No params, no other detail.
Every refusal logs one Information line `Viewer refresh refused: <Case> (<detail>), reason …, session …, viewer …`
(ids only when a session/tombstone matched; never the token or its hash). Deleting sessions (sign-in prune, new hourly
`ViewerSessionCleanup` job, account deletion) writes one tombstone per known refresh hash (current, previous, up to 8
retired) with session id, viewer id, stored reason, ended-at and expires-at = ended + 30 days; expired tombstones are
dropped by the same prune. Migration `ViewerSessionTombstones` (new table, PK = hash, index on ExpiresAt).

## Decisions
- Tombstones are written when a session row is deleted, not at revocation: a revoked row stays in ViewerSessions
  for a day (unchanged) and answers with its reason from there; the tombstone keeps it for 30 days after the session
  ended (RevokedAt, or RefreshExpiresAt for expired ones). Same behaviour to the caller, no duplicate data.
- Full SHA-256 hashes (as already stored in ViewerSessions), one row per hash, PK lookup only; no prefix matching
  (a prefix could collide and would not make lookups safer).
- Stored reasons stay as they are (logout, revoked_by_viewer, signed_out_by_viewer, revoked_by_admin,
  password_set_by_admin, two_factor_reset, password_reset, password_changed, account_disabled, session_limit,
  refresh_token_reuse); `ViewerSessionService.PublicReason` maps them to the stable public set. Account deletion is
  stored `account_deleted` and answered `admin`; two-factor reset and admin password set are `admin`; password reset
  by e-mail code is `password_changed`. Reuse-revoked sessions answer `token_reused` (additive reason; the client can
  word it like `refresh_token_reused`).
- Order: revoked beats expired (more informative); expired beats reuse checks (an expired session never revokes).
  A disabled account whose session is still live (cannot happen today: disabling revokes) answers revoked
  `account_disabled`.
- The admin console refresh (`/api/v1/auth/refresh`, AuthController) keeps `refresh_session_expired`: out of scope
  (the request is about viewer devices).
- Error codes are not part of the OpenAPI schema (free `code` string + `params` map), so the contract did not change:
  freeze-openapi byte-identical, no web/client type regeneration.
- Dev World runs at Warning; it now overrides `Streamarr.Server.Viewers.Auth.ViewerSessionService` to Information so
  refusals show in `/tmp/devworld-<port>.log` (the F8 S6 case happened on Dev World). Production default is
  Information anyway.
- The log test runs in its own serial xUnit collection: Serilog's static logger writes to the host built last, so the
  admin log feed is only reliable without parallel test hosts (same as LoggingEndpointTests).

Blocking: none.

Non-blocking:
- `POST /viewer/auth/refresh` has no rate limit (pre-B11, not `viewer-auth`). Since B11, every refusal also writes an
  Information line, so an anonymous caller can flood the log (my 1.6k probes = 1.6k lines). Suggest the viewer-auth
  limiter or sampling the Unknown line.
- An unknown token costs a `LIKE`/instr scan of `ViewerSessions.RetiredRefreshTokenHashes` (B9 code) before the
  tombstone PK lookup. Harmless at this scale.
- Account deletion writes tombstones outside the session service gate. A refresh racing the deletion could leave its
  new hash without a tombstone (that token would then answer `unknown`). Very unlikely.
- The hourly `ViewerSessionCleanup` itself has no unit test (the tests call `PruneAsync` directly); verified live below.
- `Reused` logs two lines (the existing Warning plus the new Information line).
