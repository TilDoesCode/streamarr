# M3.1 — Player spike: engines + media caps

Status: done (pending-ios: Xcode not installed; Apple engines, VideoToolbox/AVPlayer caps and Safari native HLS not run)

## Intent
One TypeScript engine interface (load/play/pause/seek/setAudioTrack/setSubtitleTrack + events state/time/buffering/
tracks/error/ended/stats) with implementations for expo-video and react-native-video 6.x (native candidates, compared),
expo-libvlc-player (VLC fallback) and web (`<video>` + full hls.js, Safari native HLS). Local Expo module
`client/modules/media-caps` (Kotlin MediaCodecList/Display HDR/AudioManager passthrough; Swift VideoToolbox/AVPlayer/
audio route; web MediaCapabilities/canPlayType) that outputs the M1.3 DeviceProfile. A `/dev/player` route: sign in via the
M2.3 account store, list Dev World variants, start each through `/api/v1/viewer/playback` with the real profile, play with
the chosen engine, metrics overlay (TTFF, seek latency, buffering, dropped frames, decoder, track switching, key events).
Measure on Google TV, Android phone and web; comparison table + engine decision; remove the losing native engine.
iOS/tvOS: pending-ios (no Xcode).

## Summary
The player spike is complete on Android (Google TV + phone emulators) and web (Chrome); Apple is pending-ios.
- **One engine interface** (`client/src/player/engines/types.ts`: `load/play/pause/seek/setAudioTrack/setSubtitleTrack`,
  events `state/time/buffering/tracks/firstFrame/error/ended/stats`, `Surface`, optional `shutdown`) with
  `expo-video` (chosen native engine), `vlc` (expo-libvlc-player 57.0.54, patched) and `web` (`<video>` + full hls.js
  1.7.3, native HLS on Safari). react-native-video 6.19.3 was implemented and measured behind the same interface and is
  removed again (package, engine file, Media3 alignment plugin).
- **media-caps** local Expo module (Kotlin: MediaCodecList HW/SW per codec with profiles, max size, bit depth, HDR
  profiles; Display HDR types/modes; AudioManager direct-playback encodings + channels. Swift: VideoToolbox HW decode,
  AVPlayer HDR modes, audio route channels. Web: MediaCapabilities (`powerEfficient` = HW) / `canPlayType`, dynamic
  range, MSE/native HLS). `buildDeviceProfile` turns the report into the M1.3 `DeviceProfile` (hardware decoders first,
  software decoders capped at 1080p, HDR = decoder ∩ display, passthrough codecs, VLC engine profile).
- **player-keys** local module (Android): takes D-pad + media keys before the Activity/MediaSession while the player
  wants them (react-native-tvos only delivers keys when a view is focused, and expo-video's MediaSession swallowed the
  media keys).
- **`/dev/player`** lab (signed-in route, linked from the dev home): lists the Dev World variants, starts each through
  `POST /api/v1/viewer/playback` with the measured profile, polls, plays with VLC when the server says so and otherwise
  with the native candidate, heartbeats progress, applies the server's track decision, switches tracks locally or via
  `/switch`, and shows a metrics overlay (server states/decision/reasons, TTFF, start-up, seeks, rebuffers, dropped
  frames, decoder HW/SW, video size/range, tracks, switch latencies, key log). "Run all" benchmarks every case and logs
  `[m31-result]` JSON rows.
- Measured every variant with expo-video, react-native-video and VLC on Google TV and the phone, and with the browser
  engine in Chrome. Every case starts through the playback API and plays as the server decided; VLC on the 2160p HLS
  transcode wedges libVLC and blocks the UI thread when it is stopped (open issue).

## Decisions
- **Native engine: expo-video.** Evidence (tables below):
  - Start-up on the TV target (the priority): expo-video had the lower TTFF on 9 of 10 native cases on Google TV (median
    243 vs 309 ms; e.g. MP4 184 vs 244, remux 133 vs 185, AV1 297 vs 374). On the phone emulator RNV was lower on 7 of
    10, but the phone numbers swing by seconds between runs (API 1.5-4 s, 4K TTFF 18-27 s), so they do not decide.
  - Seeks are equivalent (same Media3 1.9.0 underneath): Google TV remux first seek 673-712 ms vs 750-751 ms, MP4 212/285 vs
    265/315, 4K transcode 10.7/7.8 s vs 17.0/8.9 s.
  - Track state: expo-video confirmed every subtitle switch from the engine (33 of 33 benchmark switches plus the
    manual ones, 1-76 ms). RNV reported the new text-track selection for only 2 of 22 switches (the second switch on
    direct-play AV1 MKV); all 20 remux/HLS switches stayed `pending`, although the picture showed the subtitle
    (`googletv-rn-video-subtitle-by-language.png`). The UI must show what the engine really plays, so this counts.
  - HDR signalling: expo-video exposes `videoTrack.videoRange` (sdr/pq/hlg, shown as `sdr` in the table); RNV's track
    info has no range.
  - Platform fit: expo-video ships with SDK 57 (config plugin, Media3 aligned, AVPlayer on iOS/tvOS), the `VideoPlayer`
    object lives outside the view (fits the engine interface, survives overlays/remounts). RNV 6.x is the maintenance
    line while 7.x (Nitro rewrite) is still beta/alpha, and it needed a Gradle override to share Media3 1.9.0.
  - Against expo-video: no dropped-frame statistic (RNV had one via its debug EventLogger), a
    `ConcurrentModificationException` when reading subtitle tracks during track updates (retry after 100 ms), an
    always-on MediaSession that grabbed media keys (solved by player-keys), `Unknown` labels for remux audio renditions.
    None of these outweighs the above. RNV is removed (`npm ls react-native-video` → empty).
- **VLC on Android decodes with MediaCodec in copy-back mode** (`:codec=mediacodec_ndk,mediacodec_jni,all` +
  `:no-mediacodec-dr`): direct rendering showed a black picture on both emulators; copy-back shows the picture and keeps
  hardware decoding. `VlcEngine({ directRendering })` and the lab toggle allow re-testing direct rendering (zero copy)
  on real Android TV hardware.
- **expo-libvlc-player is patched** (patch-package, exact version 57.0.54): track selection by libVLC string id,
  `selected` flag per track, tracks re-emitted on `ESSelected`. Without it VLC audio/subtitle switching does not work on
  Android.
- **The client applies the server's track decision** (selected audio when delivered as `original`, selected subtitle
  when `embedded`/`webvtt`, otherwise subtitles off) once the engine lists its tracks.
- Timing definitions (uniform across engines): TTFF = `load()` → engine first-frame signal (expo-video
  `onFirstFrameRender`, web `requestVideoFrameCallback`, RNV `onReadyForDisplay`, VLC first clock advance); start =
  `load()` → clock ≥ start + 0.25 s, minus 0.25 s; seek = command → clock ≥ target + 0.25 s while playing, minus 0.25 s;
  engine switch = command → engine reports the new selection; server switch = command → new rendition plays at the old
  position.
- Logcat-based decoder detection stays a lab-only diagnostic (Android 13+ shows a system dialog on first use).

**What the emulator numbers mean.** The goldfish decoders report `isHardwareAccelerated` (decoding runs on the host
GPU), so "HW" is real host acceleration, not a TV SoC: absolute TTFF/seek values are optimistic for H.264 and say
nothing about a real device's HEVC/AV1 blocks. The emulators have no HEVC Main10, no HDR display and no AC-3/E-AC-3/DTS
decoders or passthrough, so every HDR10 variant is transcoded to SDR H.264 (`hdr_unsupported`/`bit_depth_unsupported`)
and every Dolby/DTS track is converted; HDR passthrough, Dolby Vision and audio bitstreaming are untested. The phone
emulator is CPU-starved (API calls 1.5-4 s). Conclusions that still hold: relative engine behaviour on the same
decoder (both native candidates share Media3, differences are in the wrapper), track-switch mechanics and
confirmation, server-decision handling, key routing, and the relative cost of direct vs remux vs transcode
(direct/remux start in 130-300 ms on Google TV, transcodes 360-700 ms at 1080p and 5-7.6 s at 2160p).

## Backend issues (input for M1.5)
1. **Fixed 500 ms first poll.** `pollAfterMs` is 500 for every non-final state, so an instantly resolvable start takes
   0.58-0.96 s in the API on Google TV and Chrome, while the engines then need only 130-300 ms (Google TV) or 20-200 ms
   (Chrome) to the first frame for direct/remux. A long-poll (`GET …?waitMs=`), a shorter first poll or a `POST` that
   waits briefly for `ready` would cut ~0.4 s from every start.
2. **4K transcodes are not real-time.** 2160p HEVC HDR10 → H.264 2160p (SDR): TTFF 5.2-5.6 s (Google TV), 27 s
   (phone), seeks 7-17 s, 9-13 rebuffers with both native engines. When a transcode is unavoidable and the client did
   not ask for 4K, target ≤1080p by default (or a server "max transcode height" setting).
3. **VLC is sent to HDR→SDR transcodes.** With `engine: vlc` preferred, HDR10 sources become `transcode/vlc`
   (`hdr_unsupported`), although VLC tone-maps itself; and VLC on the server's 2160p HLS transcode wedged libVLC on both
   emulators. Suggest: let the VLC engine profile declare tone mapping (direct play HDR to VLC), and return
   `engine: native` for transcode outputs (plain H.264/AAC HLS) unless the user forced VLC.
4. **Audio switch in a remux needs a new session** (one muxed audio rendition): 0.32-1.07 s on Google TV, 0.81 s in
   Chrome, 0.7-2.6 s on the phone, plus a player reload; engine-side switches take 2-120 ms. Multiple
   `EXT-X-MEDIA TYPE=AUDIO` renditions (one converted track per language) would let expo-video and hls.js switch
   locally (known M1.4 limitation).
5. **Web HDR policy (question):** Chrome on an SDR display gets `hdr_unsupported` → transcode. Browsers tone-map PQ
   themselves; the web profile could accept HDR10 on SDR displays to avoid transcodes (needs a product decision).
6. `mediaInfo.*.selected` describes the server's delivery only; after an engine-side switch the client must track the
   selection itself (not a bug, worth documenting in `docs/api.md`).
No server errors, failed playbacks or wrong decisions were seen: every fallback (`fallback_used` from the dead rank-1
release), degraded release, `vlc_fallback` (MPEG-2 on Android) and `video_codec_not_remuxable` (MPEG-2 on web) matched
the device profile.
