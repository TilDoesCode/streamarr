## Summary
(1) The transcode throttle no longer uses SIGSTOP. Mechanism: on macOS, .NET's SIGCHLD handler loops while any managed
child is *stopped* (`waitid` reports CLD_STOPPED there) and holds the process-start lock, so every Process.Start of the
server (ffmpeg, ffprobe) waited until the stopped ffmpeg resumed or died, while one core spun. Runs are now parked
(ffmpeg ended, segments kept, no process, no slot) and resumed with a new run at the parked front; throttling still
stops the CPU work and the disk growth ahead of the player. (2) The repair race: a cancelled reader's article loss
invalidated the shared capability session before the repair admission had registered the release, which cancelled
every other reader's fetch → unrepaired 500. Cancelled readers now end as cancelled, and admissions in flight count as
active repair. (3) Competing requests on one transcode session: the newer position keeps the run; a request back into
the range the last restart left waits while the newer position was used in the last 3 s (no restart ping-pong).

## Decisions
- Park = end the run instead of pausing it: works on every platform, frees the slot, costs one keyframe-aligned
  restart (~0.3 s live) when the player catches up; a resume at the parked front is not counted in `restarts`.
- Competing rule: newer position wins, the old one waits within its own wait budget (no 409: players treat a wait
  plus 504/Retry-After better than a new status), 3 s idle window, 200 ms poll.
- Repair: (a) is the actual fix of the escape, (b) closes the same window for any other failure path; no new test hook
  added for (b).
- Linux not run (Docker CLI present, daemon not started on purpose: shared 8 GB RAM); reasoning recorded above.
- No contract change (contract_check --frozen passes); no type regeneration.
