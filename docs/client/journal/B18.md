carries playback state) refreshes `repair` from the resolver's live repair status (cheap, throttled, no lock across

## Summary
During play the playback GET now reports the release's live repair state instead of the resolve-time snapshot
(F10 code review 7, P2-4): while the playback is ready and its `repair` is not terminal, each GET (at most once per
second per playback) reads the repair job and adopts its state, progress and ETA; a terminal state
(ready/failed/cancelled/evicted, or `cancelled` + `repair_job_gone` when the job disappears) stays until the playback
changes release; a repair that starts during play shows up while it runs (an old finished job does not). A fallback
to another release no longer carries the old release's repair. No contract change (the field existed); docs/api.md
and docs/viewers.md describe the live behaviour. To test it live, Dev World now publishes real PAR2 recovery for
three releases and runs progressive repair; the new robustness check `live_repair` plays a release while its repair
runs and shows the GET moving to `ready`, and to `failed` when the recovery volumes go missing. B17 verifier
leftovers: the four robustness checks pin their own session, own_flip_pacing asserts the latest request is answered,
the rest (not felt by a viewer) is in BACKLOG.

## Decisions
- Refresh on the GET only: the progress answer carries no playback state (it has no `repair` field), so it stays
  unchanged. Read outside the playback gate (in-memory coordinator lookup), apply under the gate only if revision,
  release and repair are unchanged; throttle 1 s per playback (the coordinator's fallback lookup scans all jobs).
- Known null: adopt only a running job (an old finished job of the release says nothing about this playback).
  Known non-terminal: adopt the live job (keep `progressiveEligible` for the same job, the port does not compute it).
  Job gone: `cancelled` with `failureReason: repair_job_gone` (the client treats every non-ready terminal state alike).
  Terminal sticks (spec): a later job of the same release is not reported to that playback.
- Live test via a second playback: Dev World files are small, so the server reads them ahead/materializes them at
  start and a hole cut mid-play is never met; progressive admission needs the plan's first damaged byte at resolve.
  So A starts with the hole (its repair held in downloadingRecovery by `usenet_stall` on the recovery volumes) and B
  starts meanwhile and plays at once (`repair_progressive`) — the real repair-while-streaming path.
- Dev World PAR2: generated once with the shared Par2TestWriter (cached under cache/par2/, slice size so the file has
  about 64 slices), published as extra NZB files of the release; catalog unchanged for clients (no new versions).
  Dev World enables progressive repair (256 KiB intact prefix) and lowers Repair:MinFreeDiskBytes to 1 GiB (this Mac).
- A release repairs once per instance (the server keeps the articles it read), so the failure variant uses its own
  episode (S01E25) instead of resetting server caches from Dev World.

## Follow-up (after Verification round 1, non-blocking item 1)
The B18 "fallback clears the old release's repair" branch never ran: resolve only runs while `StreamToken` is null,
and `StreamToken`/`ResolvedReleaseId` are always cleared together. Real case: X's repair fails (playback failed,
`repair` = X's `failed`), a retry `/switch {}` falls back to Y, Y plays, and the GET kept X's `failed` repair for good
(terminal, so the live refresh never replaced it). The client's repair hold (C04) reads it during play.

Fix: the playback's `repair` is tied to the release it belongs to (`RepairReleaseId`, set by every writer through
`SetRepair`: RepairAsync, the ready transition, the live refresh, a switch to another release). When the playback
becomes ready on a release, it shows that release's own repair from the resolve, else the kept one only if it belongs
to that release, else none. The release that turned ready after its own repair keeps its `ready` repair (same release).

Decisions:
- Bind instead of clearing at every resolving revision: a retry of the *same* release keeps that release's last repair
  state while it resolves again (it is X's real state), and a repaired copy reached by a retry is not stripped of its
  repair; the stale case only exists when the ready release differs, which the binding catches.
- Elephants Dream mp4 recovery raised 20 % -> 35 % (instead of a README caveat), so the README's 70-95 % hole recipe
  repairs on all three PAR2 releases (live: ready with `repaired_copy`, was "only 12 intact recovery slice(s) for 18
  damaged slice(s)"). Old r20 PAR2 cache dir deleted.
- Dev World `usenet_hole`/`usenet_stall` accept `params.releaseId` (only that version of the scoped title): needed to
  hole one version before anything reads it (a playback-scoped fault of a failed playback falls back to the whole
  title, and a helper playback caches the small file's articles).

Evidence:
