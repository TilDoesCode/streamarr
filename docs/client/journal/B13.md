# B13 — Server: playback robustness follow-ups (F10a)

Status: done

Intent: (1) seek outside the retained window restarts the transcode run (no 90 s hang); (2) per-segment wait capped
(~25 s) -> 504 + Retry-After, Retry-After on 503 segment_evicted; (3) progress answer tells a dead playback apart
(additive `playbackAlive`); (4) /switch audio fallback flag (convert selected audio to AAC). Tests, docs, OpenAPI,
types regenerated at the end. Test tree on Dev World 39310 only.

## Summary
- **(1) Seek back behind retention.** `EnsureJobForSegmentLockedAsync` reused a live run for any index between its
  start segment and front + gap, including a segment it had already written and retention had deleted: the run never
  writes it again, so the request waited for the whole budget (90 s → 504). A segment behind the run's front whose
  file is gone now counts as evicted and restarts ffmpeg at that segment (remux and transcode alike).
- **(2) Wait budget.** `SegmentWaitTimeoutSeconds` default 90 → 25, and it is now one deadline per request across all
  restart attempts (before: up to 4 attempts × 90 s) for segments, `init.mp4` and WebVTT segments. Spent budget →
  `504 segment_timeout` with `Retry-After: 1` (already set for 503/504 by `Failure`); `503 segment_evicted` now also
  carries `Retry-After: 1`.
- **(3) `playbackAlive`.** `POST /viewer/watch/progress` answers an additive nullable `playbackAlive`: null without a
  `playbackId`, true while it is a live playback of this device for this work, false otherwise (idle-expired,
  stopped, server restart, unknown id, other work). The report itself is still saved (200), so old clients see no
  change.
- **(4) Audio fallback.** `/switch { audioFallback: true|false }` (null keeps). Sticky per playback (also across track
  and version switches) until `false`. The decider gives every candidate a `ClientProfile { AudioFallback = true }`:
  direct play is blocked with `audio_fallback`, remux/transcode always convert the selected track to AAC stereo (no
  copy, no surround), no audio rendition group (`inSessionAudioSwitch` false). The decision lists `audio_fallback`;
  `PlaybackResponse.audioFallback` reports the flag.

## Decisions
- (1) Detection is "index < job.Front() and the file does not exist" under the session gate: Front() only counts
  files this run produced, so a missing file behind it can only be retention (or a manual delete). No change for
  subtitles of a transcode (still never restarted backwards).
- (2) Kept `Retry-After: 1` for 504 (the run keeps going; a quick retry usually finds the segment). 25 s chosen per
  the task. A cold transcode start slower than 25 s to its first segment now answers 504 once and the retry succeeds
  (the run is not killed by a timeout).
- (3) Additive field instead of a 404: old clients ignore it, and the watch state is still recorded. Nullable on the
  shared `WatchStateResponse` (same pattern as `available`), only set by the progress endpoint.
- (4) Fallback drops the other audio renditions (spec: "convert the selected track"; converting up to 4 tracks costs
  CPU and the client can still /switch the track, the flag stays). Not reset on a version switch (it is a device
  output problem, not a file problem). Only on /switch, not on start (the ladder step A is a switch).
- `segment_evicted` Retry-After has no automated test: the 503 is a race between the wait and opening the file and
  cannot be provoked deterministically; covered by code review and docs.

## B13b
Status: done (2026-10-05 04:46–05:4x). Follow-up from the F10 S9a live web audit (/tmp/ri/F10-S9a-web-live.md items 5 and 9).

**What.** (1) `Retry-After: 10` on a faulted 503 showed as "retry in 5 s" in Chrome. (2) After `/switch` (to transcode) on a
playback with an active `seg_status` / `seg_corrupt` / `playlist_endless` fault, the client saw `starting` for 85 s to 3+ min
(rows P2/D41, P8/C14, D10).

**Cause (1).** Not the server. Product CORS (`ViewerCorsMiddleware`) already lists `Retry-After` in
`Access-Control-Expose-Headers` for `/api/v1/viewer`, `/stream` and `/transcode`. It runs before the rate limiter, auth and
the controllers, and no exception handler clears the headers. Dev World's own CORS (`UseDevWorldCors`, before the fault
layer) exposes it too. Measured on 39310: a faulted 503 (`seg_status retryAfter 10`) sent with an `Origin` header answers
`Access-Control-Allow-Origin *`, exposes `retry-after`, and carries `Retry-After: 10`. `X-DevWorld-Fault` is in neither expose
list. The "5 s" comes from the client: hls.js does not pass fragment response headers to the app, so the countdown uses its
own default. Client note, see Open issues.

**Cause (2).** Not reproducible on the server, and not the harness:
- B12 never faults the server's own reads. ffmpeg, ffprobe, the keyframe scan and the in-process index `HttpClient` all send
  `Streamarr-Transcoder/1`, and `DevWorldFaultMiddleware.IsTranscoderRead` (UA + loopback) skips every fault without
  `internal: true`.
- `FaultPlaybackMedia` only reacts to `HlsStart`/`Probe`/`StreamAlive` faults.
- On a fresh 39310 the report's three cases all reach `ready` (transcode) in 0.3–0.5 s, including a 4-thread hammer on
  the corrupt segment (4,240 hits) and a 500 on the first switch. The fault follows the playback to the new rendition by
  design (playback scope), so the new engine fails again on the client.
- The 39300 log (read only; the server logs at Warning there, so the state machine was not visible) shows 12,576
  `seg_corrupt` hits on segment 6 from one connection in a single minute in P2. That is hls.js re-fetching a corrupt
  fragment in a tight loop (client).

There is still a real product gap: the HLS start loop had no overall budget, and `StartHlsAsync` ran with
`CancellationToken.None`. A slow or stalled source (probe 45 s + keyframe index 30 s + scan 20 s per candidate) or a starved
host could keep a revision in `starting` without limit. The test reproduces exactly that: with the fix removed, the switched
revision stays `starting` until the test gives up.

**Fix.**
- `PlaybackTimings.StartBudget` (default 60 s, `StartLimit`). `PlanAndStartAsync` hands every `StartHlsAsync` a token
  cancelled by that budget. When it fires, the revision fails with the new code `start_timeout` (suggestions `retry`,
  `lowerQuality`, …; the candidate lists `start_timeout` under `decision.skipped`). The budget is also checked between
  candidates.
- The token is deliberately not linked to switch/stop: a superseded start still completes and its late session is closed
  (existing design and tests).
- `TranscodeSessionManager.CreateAsync` takes the new session's gate without the caller's token, so a cancellation at that
  point cannot leave a registered session behind.
- Docs: api.md error table (`start_timeout`), the `starting` state row (bounded at 60 s), and a CORS paragraph (exposed
  headers, hls.js caveat).

**Tests.**
- `ViewerPlaybackTests.Switch_WhoseStartNeverReturns_FailsWithStartTimeout_WithinTheBudget`: ready playback, start gate never
  released, `/switch maxHeight 720` → `failed start_timeout` in 4.5–15 s (test budget 5 s), retry + lowerQuality, skipped
  reason. Mutation (`CancellationToken.None` again): fails, stuck in `starting`. The test host's fake start honours the token.

  seg_status/seg_corrupt/playlist_endless → ready in 0.3/0.4/0.3 s).
