transfer implementation, including a real child-process death against the repository Range server. Passing baseline
tests do not establish the integrity or lifecycle guarantees claimed by the module.

## Integrity repro details

**Crash on 200 restart (N1-02):** the unchanged Range server serves variant A; the harness seeds a 123,456-byte A
prefix, then switches the server to B. The child resumes with A's strong If-Range and receives 200. It executes the
production callback's new-validator metadata updates, actual TaskStore.save, and `Runtime.halt(0)` before the output
stream opens/truncates. Parent loads that state: the part is still A, the stored ETag is B. The unchanged Transfer
requests `Range: bytes=123456-` with B's If-Range, accepts 206, and publishes A-prefix+B-suffix as completed. The test
asserts length, both source comparisons and the preserved old prefix. ExpectedBytes is 1,048,576 throughout;
expectedEtag is omitted to exercise the API's documented optional validator. This is a deterministic kill window,
not an unsynced-page or emulator hypothesis.

**Normal control:** a 1,048,576-byte file resumes at byte 123,456 using strong If-Range; remaining body 925,120 bytes;
SHA-256 **`97034248f869e8976cec3bc5c85a2aca8722d104c022f4852e394fa3052c7bd2`**, equal to server `/admin/sha256`.
Separate controls establish 200 truncation, rejection of wrong range start/changed ETag, and ordinary 416 partial drop.

**Shared path (N1-03):** latches put two actual Transfer instances past response validation before writing the same
part. B overwrites A's inode before A's fsync/rename. A's size checks all pass because the sizes are equal. This is why
size verification alone does not repair target collisions.
