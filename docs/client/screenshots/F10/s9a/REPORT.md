## FAIL rows — repro and suspected code

1. **START / C21 / C12 / C08 / D29 / D36 — black 0:00 with neither spinner nor hint (root cause shared).**
   - Repro: arm `{"fault":"seg_delay","scope":{"next":"anna"},"target":"video","params":{"ms":6000},"mode":{"count":2}}` and open `/play/new?workId=tmdb-movie-45745&start=90` in Chrome. You get 6.5 s of black 0:00 with no spinner.
   - Mechanism: in hls.js mode the web engine emits a `time` event with `currentTime 0` before hls.js applies its `startPosition`. The `startSeek` guard in `client/src/player/engines/web-engine.web.tsx:223-236` only applies in native mode, where `startSeek.target` is 0. The controller treats any clock ≥ 0.5 s away from `loadPosition` as a picture, at `client/src/player/controller.ts:700` (`if (!this.pictured && Math.abs(event.position - this.loadPosition) >= 0.5) this.onPicture()`).
   - Result: `onPicture()` (`controller.ts:918-924`) sets `pictured=true` and `loadingSince=0`. That removes the loading spinner (`recovery/status.ts:89-94`) and the start budget (`controller.ts:1059-1061`), so a source that never delivers stays black for good. This is the C12 after step-down, D36 and C21 cases.
   - Every reload, new start or step-down at position > 0 (`controller.ts:744-748`) hits the same path.
   - Fix direction: count a picture only on the engine's `firstFrame`, or on a clock that moved from the load position.
2. **C10 503 (and the interim hint of C10-404, C17, P4) — a server error is shown as "buffering" with "Lower quality".**
   - hls.js retries fragment errors 6× with up to 8 s between them (`FRAG_LOAD_POLICY.errorRetry`, `web-engine.web.tsx:38-45`), and non-fatal errors are dropped (`web-engine.web.tsx:369`). The app therefore learns about a 503/404 only after ~31 s.
   - Meanwhile `statusOf` shows `buffering` + `lowerQuality` (`recovery/status.ts:95-99`, `stallHint`).
   - Fix direction: forward non-fatal `fragLoadError` with an HTTP status so the hint can name the server, or lower `errorRetry` for 5xx/404.
3. **C08 — a slow transcode is called "Slow connection 0.6 of 2.2 Mbit/s".** `stallHint` (`recovery/status.ts`, after line 125) compares the hls.js bandwidth estimate with the bitrate. With `method === 'transcode'` the measured throughput is the server's encode rate, so the server-slow hint ("The server converts slower than playback", C08) never shows.
4. **D36 / C20 — a failed audio split goes down the quality/network ladder.**
   - Repro: `{"fault":"split_abort","scope":{"playbackId":P},"rendition":"1","params":{"afterBytes":4096},"mode":"always"}` mid-play (Sintel, German audio).
   - No `audioError` is emitted: `audioErrorCode` in `client/src/player/engines/hls-audio-error.ts` does not match aborted audio fragment loads. So it becomes a T5 stall → Q → black (item 1) → "Verbindung unterbrochen" loop with no card after 3+ min.
   - Expected: "Kein Ton. Audio wird neu geladen …" → `/switch {audioFallback}`.
5. **P2/D41, P8/C14, D10 — an unbounded switch.**
   - After `/switch` (to transcode) the server keeps the playback in `starting` (85 s in P2, 3+ min in P8 and D10) while the client polls every 0.5 s.
   - `statusOf` returns `NONE` for `phase === 'switching'`, and `STATE_BUDGET_MS.starting` (45 s) is only checked for `phase === 'starting'` (`recovery/status.ts:78-85`). The viewer sees "Wird umgeschaltet… / Stream wird geöffnet." over a frozen frame with no budget, hint or card.
   - Server side to check: why a transcode run started by `/switch` on a playback with an active `seg_status`/`seg_corrupt`/`playlist_endless` fault never reaches `ready`. Possibly the Dev World fault also catches the server's own readiness read, so this may be a harness artefact. The missing client budget is real either way.
6. **D10 (Safari native HLS).**
   - A media playlist without `ENDLIST` makes Safari treat the stream as live. After the reload or step-down, playback restarted at 0:21 instead of 0:59 (duration "unbestimmt"). The ladder then continued from the wrong position ("es geht weiter bei 0:29").
   - The status hint's action button renders as an **empty white pill with no label** on iPhone Safari (`d10-safari-hint-blank-button.jpg`; Chrome renders "Niedrigere Qualität"). Suspect: the status-layer button text style in `client/src/screens/player/player-status.tsx` on WebKit.
7. **E09.**
   - After `engine.load` throws in an N step, the old hls.js source keeps playing until its buffer runs out. The runner then classifies the stall as T5 and runs Q.
   - Q calls `/switch` on a playback the server already closed → `playback_not_found` → the card "Wiedergabe beendet" instead of "Interner Fehler im Player / player_internal_error".
   - Suspect: the N/restore path in `controller.ts` (no engine teardown when `load` throws; the failure is not terminal for the incident) and runner categorisation.
8. **B06.**
   - With `transcode_never_start` on every HLS start, the ladder ran N, N, N and then a card, although a direct-play mp4 release of the same title exists. The V step ("Trying another version at …") never ran.
   - Suspect: `client/src/player/recovery/ladder.ts` (V not reachable from category of `transcode_failed` at N) or `recovery/other-version.ts` (`nextVersion`).
9. **P8 minor:** `retryAfter: 10` showed as "Neuer Versuch in 5 s". Either `Retry-After` is not readable cross-origin by hls.js/fetch, or it is not forwarded.
