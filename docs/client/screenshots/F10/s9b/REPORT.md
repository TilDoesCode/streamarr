## FAIL rows — repro and suspected code

1. **D36/C20 Exo — a dead audio rendition is called "Connection lost".** Repro: Google TV, Sintel remux, `split_abort {target: audio, rendition: "1", afterBytes: 4096, mode: always}` on the playbackId while the buffer is short (throttle video to 900 kbps first). Exo fails with `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED`. `recovery/classify.ts:118` (`OFFLINE`) makes it T1 `network_unreachable`, so the viewer gets "Connection lost. Retrying in N s…" with backoff 2/4/8/16 s and finally a new start (which only works because the new playbackId escapes the fault). The audio ladder (reload audio → `/switch {audioFallback}`) never runs. Suspected: the expo-video patch reports no track type / URL for the failing load, so the controller cannot tell an audio-rendition failure from a network loss. NetInfo said online the whole time and the video kept loading, so "offline" is contradicted by the evidence.
2. **D41/E14 Exo — one bad segment skips the reload and blames the device.** Repro: `seg_corrupt {target: video, mode: garbage, mode: always}`. `ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED` → T7 `decode_error` (classify.ts:114–115 `DECODER`/`PARSER` order) → step S at once (no reload) → notice "Switched to VLC… This device couldn't decode the video." (status.ts decoder hint). The data was corrupt, the device decoder is fine; with `mode: once` Exo even recovers on its own. Expected (matrix D41): reload once, then step down with an honest reason.
3. **C08/R4 Exo — a slow server ends in "The picture didn't appear".** Repro: `transcode_slow {readrate: 0.5, mode: always}` on the playbackId, then pick 720p. `controller.ts:1216-1223`: the start budget expires on a transcode that is only slow and raises T7 `picture_timeout`. The ladder then reloads, steps down (`no_more_methods`), switches to another version (also without a picture in 30 s) and ends on the picture_timeout card after ~2.5 min. The first 27 s correctly said "The server converts…". Expected: "The server converts slower than playback" and lower quality / keep waiting, never a decoder-style card. Secondary: the switch resumed at 0:59 (the position before Replay + seek to 0:20) instead of 0:20. Seen once; likely `resumePosition`/`lastGoodPosition` not updated by a seek made shortly before the switch.
4. **C12/C18 Exo — endless playlist = false "FINISHED".** Repro: `playlist_endless {segments: 10}` `next:anna`, start at 0:40. Exo reports duration 60 and `ended` at 0:59. `controller.ts:959-969` `onEnded()` compares the position with the **engine** duration (`getSnapshot().duration` = 60), so `position >= duration - 3` → `finish()`. `mediaInfo.durationTicks` (180 s) is ignored there, while the `duration` getter (`:343`) also prefers the engine value. Same root cause as the web C12 FAIL in S9a2.
5. **VLC start at a position (Google TV) — frozen 0:00 frame + "The connection is slow." for ~20 s.** Repro: on a playing remux call `setEnginePreference('vlc')` (or let D41 step down to VLC). VLC presents ~5 frames of 0:00 and stalls. `status.ts:186-193` `slowCause()` says `slowConnection` for any non-transcode/remux method (here direct on loopback). Only the 20 s `picture_timeout` reload gets it playing at the position. Suspected: `engines/vlc-engine.tsx` start-time handling (the seek to the start position right after `Playing`), or the start budget is too long for a direct VLC start that decoded frames and stopped.
6. **C22 Exo — failed subtitles vanish silently.** Known S6m gap ("native engines still emit no `loadRetry`/`subtitleError` events"). Row C22 is closed only for the web engine; on Exo the viewer is never told the German subtitles are off.
7. **A12 on Google TV — "Paused: screen locked."** for a pause that came from an incoming intent (deep link while playing). The expo-video background pause maps to `locked` (patch, S6). On a TV, `outside the app` would be the honest text. Minor.
8. **Cosmetic, all Exo reloads/switches (R5/E18):** while "Playback stopped. Resuming at 0:41…" / "Switching to a lower quality… at 0:41" shows, the picture is the **new source's 0:00/0:01 frame**, not black and not the last frame (gtv-exo-c11-503-21s, gtv-exo-r6-stall-40s, gtv-exo-d36-audio-26s). expo-video shows the first decoded frame before the seek to the position lands. Not counted as a separate FAIL.

### FAIL rows (turn 2) — repro and suspected code

1. **AVPlayer hides segment HTTP errors (C10 404, C11 503).** Repro: iPhone, remux or transcode, `seg_status {target: video, status: 404|503}` on the playbackId. AVPlayer retries quietly and never raises an error. The JS layer sees only a stall, so the ladder runs **Q** (lower quality) with "Loading takes longer…" or "**The server converts slower…**" (`status.ts` `serverSlow`/`buffering` by method). For a gone session (404) it then lands on the **"No picture appeared / picture_timeout"** card, because the stepped-down source of the same dead playbackId never shows a frame (`controller.ts:1216-1223` start budget). Expected: N (new start) for 404, and "Problem on the server, retrying" for 503. Suspected fix area: the patched expo-video iOS probe (S6) gives no `loadRetry`/access-log errors (S6m "Open"). `AVPlayerItem.errorLog()` / `AVPlayerItemNewErrorLogEntry` carry the HTTP status per segment request and could feed `classify.ts` the way the Exo HTTP status does.
2. **Second server loss within the incident window ends on a card (B25, iPhone).** Repro: `playback_gone` once (silent N), then on the new playbackId ~95 s later. The stall goes to **S**, `/switch` answers 404, and the runner stops with "Playback ended — playback_not_found" instead of a second N. Suspected: the runner's per-incident budget for N (`recovery/runner.ts`) is not reset when the earlier N succeeded and played. Also, `playback_not_found` from `/switch` during S should map to N, not end.
3. **D36 audio on AVPlayer:** an aborted audio rendition → stall → "server converts slower" → S (no other method) → **V (another version)**. The viewer loses their subtitle language and never learns it was the sound. Same root cause as 1 (no error detail from AVPlayer). The T7 `audio_rendition_failed` path never triggers on iOS.
4. **C22 on AVPlayer:** a 404 on a WebVTT rendition **stalls the whole playback** (AVPlayer waits for the subtitle segment) and ends on the "No options left" card. This is worse than turn 1's Exo C22, where the subtitles just vanished. Suspected: native HLS subtitle renditions on iOS. Options: the client could detect "stall while the selected subtitle is not empty" and turn subtitles off as the first step, or the server could leave a failing subtitle rendition out (or serve it empty) for AVPlayer.

### Summary (turn 2)

On AVPlayer, everything that only the heartbeat can see (server restart, lock) is handled cleanly. Everything inside the HLS delivery (404/503 segments, audio rendition, subtitle rendition) reaches the app only as an unexplained stall. The ladder then explains it with the wrong cause ("server converts slower"), lowers the quality for no reason, and in three of five cases ends on a card that names the wrong problem (`picture_timeout`, `no_more_methods`, `playback_not_found`). Apple TV and iPad segment rows can't be reproduced with 3-minute Dev World clips: tvOS/iPadOS AVPlayer buffers the whole clip in seconds. They need a longer clip, or a fault armed before the first segment, e.g. a `next:` `seg_status` with an `after` segment index.
